| **开源交付质量** | 零自动化测试、无规范文档。 | **100% 覆盖核心逻辑的单元测试套件** + GitHub Actions 多版本跨平台 CI 流水线 + 完整开源规范。 |

## ⚡ 极速启动与使用指南

### 1. 运行环境要求
- Python 3.9 或更高版本（原生内置 sqlite3 与 http.server，无需额外安装 pip 包）。

### 2. 方式 A：启动企业级交互式 Web 工作台（推荐 ⭐⭐⭐⭐⭐）
```bash
# 启动本地高可用 REST API 与单页工作台服务
python run.py --web --port 8088
```
打开浏览器访问：**`http://localhost:8088`**  
系统已内置三类测试账号（支持在登录界面一键填入）：
- 🧑‍💼 **年审主审审计员**：`auditor` / `auditor123`
- 🏪 **星澜电商运营主管**：`operator` / `operator123`
- ⚙️ **超级管理员**：`admin` / `admin123`

### 3. 方式 B：CLI 命令行全量压测与 A4 报告导出
```bash
# 自动生成 1000 笔真实业务压测流水，执行三方对账与试算平衡，导出像素级 HTML 审计报告
python run.py --count 1000
```
生成的审计报告位于：`data/reports/audit_reconciliation_report.html`。

### 4. 运行全量自动化单元测试
```bash
python -m unittest discover tests -v
```

## 📦 真实电商 12 种典型脏账注入场景

系统内置的 `DirtyDataGenerator` 还原了小微电商在真实大促、跨期结算中必定踩坑的 12 种边界故障：

| 场景编号 | 真实业务暗坑 | 系统识别状态 | 会计调账分录建议 (Audit Workpaper) |
|---|---|---|---|
| **01** | **正常全额履约订单** | `MATCHED` | 借：银行存款 / 贷：主营业务收入（自动平账） |
| **02** | **跨月退款退货冲销** | `TIMING_LAG` | 借：主营业务收入（红字） 应交税费-应交增值税（销项红字） / 贷：银行存款 |
| **03** | **运费险理赔周期滞后** | `LOGISTICS_MISMATCH` | 借：其他应收款-运费险理赔 / 贷：销售费用-运费补贴（待保险入账冲减） |
| **04** | **平台类目佣金跳档暗扣** | `FEE_DISCREPANCY` | 借：销售费用-平台技术服务费（暗扣提点） / 贷：银行存款 |
| **05** | **满减券退款分摊舍入尾差** | `AMOUNT_MISMATCH` | 借：财务费用-结算尾差 / 贷：应收账款-渠道结算 |
| **06** | **支付千六费率截断误差** | `AMOUNT_MISMATCH` | 借：财务费用-手续费差异 / 贷：银行存款 |
| **07** | **快递超重未报备后补扣费** | `LOGISTICS_MISMATCH` | 借：销售费用-仓储物流费（超重补扣） / 贷：应付账款-物流承运商 |
| **08** | **破损补发导致单据一对多** | `LOGISTICS_MISMATCH` | 借：营业外支出-运输破损损耗 / 贷：应付账款-物流运费 |
| **09** | **支付成功但业务系统掉单** | `UNILATERAL_CHANNEL` | 借：银行存款 / 贷：其他应付款-待查长款（待查明补录或退回） |
| **10** | **业务下单超时未支付关闭** | `UNILATERAL_BIZ` | 不产生财务流水，系统自动识别为未付订单并关闭 |
| **11** | **T+1 跨行跨日清算在途** | `TIMING_LAG` | 借：其他货币资金-在途清算资金 / 贷：应收账款-收单网关 |
| **12** | **并发网络抖动重复扣款** | `UNILATERAL_CHANNEL` | 借：银行存款 / 贷：其他应付款-重复扣款待退 |

## 🎤 面试高频问题攻防手册（姜姐 + 老默专业指导）

### Q1：为什么你的项目没有用市面上现成的大型支付框架（如 Jeepay）？
> **老默视角回答**：  
> “通用开源支付中台往往偏重底层的收单网关协议对接，是针对大中型企业的巨石 Java 架构，根本不解决电商垂直业务‘最后一公里’的深水区痛点。小微电商（如月 GMV 10 万的微利盘子）真正亏钱的地方全在跨月退款、运费险理赔滞后、平台阶梯抽佣和运费超重罚款等隐形损益上。我自研的核心状态机聚焦于**业务订单、渠道资金、仓储物流的三方交叉核验**，并引入复式记账试算平衡自检，研发 ROI 远高于盲目部署臃肿中间件。”

### Q2：数据量涨 10 倍（10 万笔）甚至 100 倍时，这个系统坏在什么地方？
> **老默架构评审三问**：  
> 1. **它坏在什么地方？** 瓶颈首先出现在单机 SQLite 写入锁与全量单表加载的内存占用上。  
> 2. **涨 10 倍怎么改？** 第一步将单表全量加载改为基于 `order_id` 哈希分片或分页游标批处理；第二步将 SQLite 存储引擎水平无缝迁移至 PostgreSQL，开启连接池与并发行级锁。  
> 3. **怎么知道它坏了？** 系统内置了 `audit_logs` 审计追踪与试算平衡断言，一旦 `unexplained_diff != 0.00`，立即触发报警截断。
